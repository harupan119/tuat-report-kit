# TUAT レポート作成（spec → 執筆 → ゲート → 提出前チェック）

演習・実験レポートを、**先に設計図（spec.json）を作ってから**ブロック（節）ごとに書き、機械検査（ゲート）を通して仕上げる。
本文を書くのはエージェントでも本人でもよい。どちらの場合も、書いた後に同じゲートを通す。

| 工程 | 道具 |
|---|---|
| 構成・体裁・引用の規約 | `references/guidelines.md` |
| 設計図 | `templates/spec.example.json` を写す / 既存の下書きからは `scripts/derive_spec.py` |
| 執筆 | エージェントまたは本人（下の「執筆のルール」） |
| 機械検査 | `scripts/report_gate.py` |
| 提出前チェック | `references/validation.md` |
| PDF | `tuat-report-pdf` スキル（表紙は作らない） |
| 科目ごとの知見 | 本人の科目メモ（雛形 `templates/course-memo.md`） |

コマンドは `python`（macOS では `python3`）。標準ライブラリだけで動く。

## 0. 着手前に確かめること

1. **課題PDF**（採点基準・提出物・字数・締切）。規約と食い違ったら課題PDFを正本とし、差異をレポートに明記する。
2. **生成AIの利用規定**。課題・科目・所属の規程が、生成AIによる本文作成を禁じていたり、利用の記録を求めていたりしないか。禁じられていれば、エージェントは本文を書かず、構成の相談と検査だけに回る。
3. `references/guidelines.md`（構成・体裁・引用）と、あれば学科配布の「レポートの書き方」。
4. 対象科目の科目メモ（あれば）。固定値・ファイル名・落とし穴を先に読む。
5. 実測データ・図・ソース。**実測していない値は作らない**。

## 1. spec.json を作る

`templates/spec.example.json` を作業フォルダに写して埋める。1ブロック = 1つの節。

| キー | 中身 |
|---|---|
| `title` / `register` | 題名 / `academic`（だ・である調。既定）か `polite` |
| `blocks[].id` / `role` / `heading` | 識別子 / 序論・手法・結果・考察・結論 など / 本文の `##` 見出しと完全に同じ文字列 |
| `blocks[].target_chars` | 目標字数（空白を除く）。ゲートは `expansion_ratio`（既定 0.85〜1.4 倍）の外を不合格にする |
| `blocks[].points` | その節で**必ず書く要点**。ここに無い主張を本文で足さない |
| `blocks[].terms` | 言い換えてはいけない用語（表記揺れも検出する） |
| `blocks[].facts` | 本文にそのまま出すべき値（例 `誤検知率 4.2%`）。実測データから写す |
| `gates` | 閾値の上書き（任意）: `expansion_ratio` / `dup_warn_pct` / `dup_fail_pct` |

構成は `references/guidelines.md` の「レポート構成」に沿わせる（はじめに → 方法 → 結果 → 考察 → おわりに → 参考文献）。
既に下書きがある時は `python scripts/derive_spec.py report.md -o spec.json` で用語と字数を起こし、`points` と `facts` を足す。

```bash
python scripts/report_gate.py spec.json --validate-only   # spec の形だけ確かめる
```

## 2. 本文を書く

`report.md` に、spec の `heading` と同じ `## 見出し` で節を並べる。先頭の `# 題名` は PDF の1ページ目に題名として出る。

### 執筆のルール（エージェントが書く時も本人が書く時も）

- 各節は spec の `points` を全部、その順で書く。points に無い主張・数値・出典を足さない。足したい時は先に spec を直す。
- `facts` の値・単位は一字も変えない。結果の節は事実だけを書き、解釈は考察の節に書く。
- 考察は結果の数値を引用し、「何が起きたか」だけでなく「なぜか」を書く。
- 出典は書籍・論文など信頼できるものだけ。番号は `[1]` から連番、引用していない文献は載せない。生成AIの出力を出典にしない。
- 図表は本文で必ず言及する。表は `**表1: …**` を表の直前、図は `**図1: …**` を図の直後に置く（tuat-report-pdf が拾う形）。
- 話し言葉・誇張した言い回し（「画期的」「浮き彫り」など）・全角ダッシュを使わない。

### 長いレポート

節ごとに独立して書けるので、エージェントは節単位で分担してよい（並列に書いて、最後に節の順に結合する）。分担しても、各節は spec のその節だけを入力にし、他の節の内容を推測で補わない。結合後は隣の節との重複をゲートが見る。

## 3. ゲートを通す

```bash
python scripts/report_gate.py spec.json report.md               # ✗ があれば exit 1
python scripts/report_gate.py spec.json report.md --json gate.json
```

| 区分 | 検査 |
|---|---|
| 不合格（✗） | 字数の範囲外 / 用語の消失・表記揺れ / facts の改変・欠落 / だ・である調への です・ます調の混入 / 「閾値を越える」型の誤用 / 隣の節との重複率が `dup_fail_pct` 超 |
| 警告（⚠） | 簡易 AI 臭（誇張語・「することができ」・全角ダッシュ・太字ラベル）/ 英語混入の疑い / 重複率が `dup_warn_pct` 超 |

不合格のブロックだけを書き直して再検査する。**同じブロックが3回続けて落ちたら書き直しを止め**、spec（points・target_chars・facts）が課題と合っているかを本人と確かめる。警告は内容を見て、意図した表現なら残してよい。

## 4. 提出前チェック

`references/validation.md` を上から確認する（指示の監査・内容・体裁・番号の連番・PDF・ZIP）。科目メモにある科目固有のチェックも行う。

## 5. PDF にする

`tuat-report-pdf` スキルで `report.md` から PDF を組む（表紙は作らない。課題が表紙を求める場合は別途用意する）。PDF を作った後に本文を直す時は、`report.md` を直して組み直す。PDF や Typst を直接直さない。

## 6. 生成AIの利用記録

課題が利用記録を求める場合は、使ったツール・モデル・何をさせたか（構成の相談・執筆・検査）を事実どおり記録する。エージェントが書いた節は、そう書く。

## 科目メモの育て方

1本仕上げたら、再利用できる知見（提出形式・ファイル名規則・固定値・効いた工夫・落とし穴）を科目メモに追記する。雛形は `templates/course-memo.md`。次回はそれを読んでから着手する。
